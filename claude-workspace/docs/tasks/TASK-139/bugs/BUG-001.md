## Detail Design Reference
`src/pages/hr/PayrollPage.tsx` — table header (`<thead>`) and footer (`<tfoot>`) of the payroll table.

## Test Scenario
Manual/code-level verification of reviewer focus area 5 (no automated test exists for this — confirmed

## Expected Behavior
Per the implementer's own handoff ("Table `tfoot` colSpan updated (13→14) for the new column") and the
reviewer's ruling ("`tfoot` colSpan correctly bumped 13→14 for the new column"), the intent is that the
"Tổng thực nhận" (total net pay) value cell in the footer continues to render directly under the
**"Thực nhận"** header column, exactly as it did before this task added the "In phiếu" (print) column.

## Actual Behavior
The value cell now renders under the **"In phiếu"** (print icon) column instead — one column to the
right of "Thực nhận". This is a straightforward consequence of HTML `colSpan` column-occupancy rules,
not something a screenshot is needed to establish:

- `PayrollPage.tsx:178-194` — the `<thead>` row has **15** `<th>` cells after this task (14 data columns
  + the new "In phiếu" column at position 15).
- `PayrollPage.tsx:200-250` — each `<tbody>` `<tr>` correspondingly has **15** `<td>` cells (confirmed by
  direct count), so column widths/positions line up 1:1 with the header.
- `PayrollPage.tsx:254-263` — the `<tfoot>` row is:
  ```tsx
  <tr>
    <td colSpan={14}>Tổng thực nhận</td>
    <td>{formatCurrency(data?.total_net ?? 0)}</td>
  </tr>
  ```
  A `colSpan={14}` label cell occupies columns **1–14** (i.e. through "Thực nhận", which is now column
  14). The following un-spanned `<td>` (the actual total value) therefore lands in column **15**, which
  is the **"In phiếu"** header — not "Thực nhận".

**Before this task** (`git diff 4bf1b55 d59942f -- src/pages/hr/PayrollPage.tsx`), the header had 14
columns (ending at "Thực nhận") and the footer used `colSpan={13}` — spanning columns 1–13 (through
"Điều chỉnh"), so the un-spanned value `<td>` correctly landed in column 14 = "Thực nhận". That was
correct.

TASK-139 added one new header column ("In phiếu") **and** bumped the footer `colSpan` from 13 → 14. But
adding a header column while keeping the same "value cell is un-spanned, immediately after the label"
structure requires the `colSpan` to **stay at 13** (still spanning through "Điều chỉnh"), so the value
cell keeps landing on "Thực nhận" (still column 14) — the new "In phiếu" column (15) would then simply
have no cell in the footer row (visually blank there, which is fine/expected for an action column).
Bumping `colSpan` to 14 was the wrong fix: it shifts the *label* to end at the new "Thực nhận" position,
pushing the *value* one column further right, under "In phiếu".

## Steps to Reproduce
1. Open PayrollPage for any month with at least one payslip.
2. Look at the table footer row ("Tổng thực nhận" + the total amount).
3. Compare the total amount's horizontal position against the "Thực nhận" column values above it, and
   against the "In phiếu" (print icon) column.
4. Expected: total amount is directly under "Thực nhận" (col 14). Actual: total amount is directly under
   "In phiếu" (col 15).

This can also be confirmed purely by reading the source (no runtime needed): count `<th>` in `thead`
(15), then walk the `tfoot` row's `colSpan` sum (14) + 1 unspanned cell = 15, landing the value in
column 15.

## Impact
- **User impact:** Accounting staff reading the payroll table footer will see the period's total net
  pay amount aligned under the print-icon column, not under "Thực nhận" — confusing at a glance,
  especially since the print column has no other numeric content to explain the value's position.
- **Business impact:** Low — the number itself is correct (`data.total_net`), this is purely a visual
  misalignment, not a data-correctness bug. No financial figures are wrong, and the Excel export
  (separately verified in this test round) is unaffected.
- Not caught by any existing or new automated test (neither `PayrollPage.test.tsx` nor
  `PayrollPage.export.test.tsx` asserts on the footer/colSpan), so this is a real gap the reviewer
  explicitly flagged as needing verification.

## Suggested Fix
`src/pages/hr/PayrollPage.tsx:256` — revert `colSpan={14}` back to `colSpan={13}` (i.e. do not bump it;
the new "In phiếu" column is an action column that doesn't need a footer total under it). That keeps the
un-spanned value `<td>` landing in column 14 ("Thực nhận"), matching pre-TASK-139 behavior, with column
15 ("In phiếu") simply empty in the footer row.

Optionally, add a regression test asserting `screen.getAllByRole("columnheader")` count matches the
number of cells summed in the `tfoot` row (colSpan-aware), so this class of off-by-one doesn't slip
through silently again.

### Root Cause

The `tfoot` label cell's `colSpan` was bumped from `13` to `14` when the
"In phiếu" print column was added, on the incorrect assumption that colSpan
should scale with header count. Since the un-spanned value `<td>` lands
immediately after the label span, colSpan=14 pushed it from column 14
("Thực nhận") to column 15 ("In phiếu").

### Changes Made

- `src/pages/hr/PayrollPage.tsx`: reverted the `tfoot` label cell to
  `colSpan={13}` (exactly as suggested in this report), with an inline
  comment explaining why it must stay at 13 regardless of trailing action
  columns.
- `src/tests/hr/PayrollPage.export.test.tsx`: added a regression test
  (`PayrollPage — TASK-139 footer alignment regression (BUG-001)`) asserting
  the label cell's colSpan equals the 0-based index of the "Thực nhận"
  header, guarding against this off-by-one recurring on a future column
  change.
